# Almena Wallet — notes for contributors and agents

The user's app for Almena ID, a decentralised messaging platform based on DIDComm Messaging v2.0
(https://identity.foundation/didcomm-messaging/spec/v2.0/). It talks to an Almena mediator (`../mediator`).

This project is independent: it has its own tooling and shares nothing with `../mediator` except the protocol.

## Layout

- `src/` — React + TypeScript front end (Vite). Package manager: pnpm.
- `src-tauri/` — Tauri v2 Rust side (`wallet_lib`).
  - `identity/`: BIP-39 phrase → seed → SLIP-0010 `m/0'` → ed25519 `did:key`. The derivation is frozen and pinned by test vectors; changing it makes existing phrases open a different identity. The seed is held in memory while the wallet is open and never crosses to the front end. The phrase is never kept, so it cannot be shown again; Profile → Security → Check your recovery phrase (`PhraseCheckScreen`, `src/phraseCheck.ts`) asks for the PIN — or biometrics, or on an iPhone without one its own lock — through `vault_confirm` (`attempt`, or `presence::open` with the key proven against the record), which marks `Held` confirmed for five minutes (`CONFIRMED_FOR`, dropped with the seed and on every `adopt`); only then does `identity_check_phrase` read the typed words as a restore does (`phrase::read`, `seed_of`), compare their seed with the open one in constant time (`subtle`) and answer yes or no (`identity_unconfirmed` without it). The words are neither stored nor logged.
  - `vault/`: the seed on the device between launches — a versioned record (Argon2id + XChaCha20-Poly1305, 10 PIN attempts) kept in the platform's secret store, or on Android a private file sealed again (AES-256-GCM, `almena-keystore/1` prefix) under a key the Android Keystore generates and never releases — StrongBox where there is one, the TEE otherwise — by this repository's own plugin, `src-tauri/plugins/keystore` (Rust in `src/`, Kotlin in `android/`, pulled into the Gradle project by tauri-build however often `gen/android` is regenerated); a record written before it is sealed the first time it is read, and one the Keystore cannot open (a restore from a backup, which never carries the key) reads as unreadable, so the phrase is the way back. The record is left out of the system's backups and device transfers (`src-tauri/backup/`, put into the manifest by `push/sync.sh`): it would open nowhere else. Security shows which (`keystore`). Every PIN check goes through `attempt`. **How short a PIN may be follows where the record is kept** (`store::hardware_bound`, `vault::shortest`): four or six digits where hardware keeps it on the device — the iOS Keychain item (`this-device-only`) and the file sealed under the Android Keystore —, six everywhere a process of the same user could copy it off and try every PIN offline: Windows, Linux, macOS (the record is in the file keychain on every build, signed or not; only the device key reaches the data protection keychain) and an Android file the Keystore would not seal. A new or changed PIN shorter than that is `vault_pin_too_short`; `vault_status` says `minDigits` and, for a record holding a shorter one, `lengthen`, and `App.tsx` then puts `PinChange` (no way back, the digits just typed handed over as `known`) between the unlock and the tabs until it is six. `vault_destroy` removes nothing unless told `confirm: "sign-out"` (`vault_unconfirmed`), which only the sign-out screen sends. Changing the PIN rewraps the data key and leaves the seed as it was. Biometrics put a copy of the data key where the system holds it behind its own presence check, one `Keeper` per platform in `presence.rs` (`presence/android.rs`, `presence/hello.rs`) with the rules shared and tested once there (`arm`, `disarm`, `open`, `changed`), so the front end sees only `deviceUnlock`, `deviceKey`, `deviceChanged` and which system it is (`biometrics`: `apple`, `android`, `windows`, worded by `src/biometrics.ts` — "Biometrics", "Fingerprint or face", "Windows Hello"): the protected keychain on iOS and, on a signed macOS build with a sensor (probed at startup), the data protection keychain (`require-user-presence`), where arming is proven by reading the key back; on Android a second Keystore key (`almena-vault-biometric`: AES-256-GCM, StrongBox where there is one, `setUserAuthenticationRequired` with `AUTH_BIOMETRIC_STRONG` per operation — validity -1 before API 30 —, `setInvalidatedByBiometricEnrollment`) whose cipher only a `BiometricPrompt` with a `CryptoObject` unlocks (androidx.biometric; strong biometrics, negative button "Use PIN", words handed over by the front end as `prompt`), the sealed copy in `vault.biometric` beside the record and left out of backups like it; on Windows a Windows Hello key (`KeyCredentialManager`, `almena-wallet`) signs a random 32-byte challenge — PKCS#1 v1.5, deterministic — and HKDF-SHA256 of the signature wraps the data key (XChaCha20-Poly1305), challenge and wrap kept in the Credential Manager under `hello-key`; the Hello prompt cannot be parented to the window (no HWND variant). Linux has no standard presence API and does not offer it. Arming always costs the PIN, and on Android and Windows sealing itself answers the prompt. A copy the system can no longer hand back — a fingerprint or face enrolled since, Hello reset — is `deviceChanged` (asked without a prompt), `vault_device_changed` when tried; the record is disarmed then or at the next PIN opening, the lock screen says why, and the PIN opens it as ever. Signing out removes every copy (`store::clear`). **On an iPhone with a passcode there is no PIN**: the record (version 2) carries no PIN wrap and the data key is kept with `userPresence` + `WhenPasscodeSetThisDeviceOnly` (`store::set_device_lock`) — Face ID first, then the passcode; the lock screen is `DeviceLockScreen`. A PIN is chosen only where the iPhone has no passcode, and a PIN wallet moves over on its next opening once there is one. Removing the passcode deletes the key, and the phrase is the way back.
  - `messaging/`: the mediation with a DIDComm mediator and the relationships through it, on `almena-didcomm` (git dependency on `../mediator`'s repository, pinned to a tag). Every DID is a `did:peer:2` derived from the seed whose service routes through the mediator (`peer.rs`): the inbox (`m/1'`, keys the mediation, never shared), the contact card (`m/4'`, named by the wallet's OOB invitation) and one pairwise per counterparty (`m/3'/…`, from a hash of the counterparty's DID). DIDs other than the inbox are registered with a possession proof. A relationship opens with a Trust Ping from the accepter's pairwise to the card, answered from a new pairwise with `from_prior` signed by the card (`contacts.rs`); whoever holds the invitation may open one, but past `WELCOMES` (20) opened through the card in a day with nothing said in them a stranger's ping is dropped (`welcomed` marks them). A message from anyone but the relationship's current pairwise, and any type the wallet does not speak, is acknowledged and dropped rather than left queued. The mediator and the relationships are sealed under `m/2'` (`state.rs`); no secret key is stored. Requests to the mediator are authcrypted with `return_route: "all"`, and each operation re-sends the idempotent `mediate-request` first. Its answers are read under 24 MiB (`ANSWER_BYTES`: a `delivery` of `DELIVERY_LIMIT` messages, never more than a mediation's 10 MiB queue, base64 twice over) and a `did:web` document under 1 MiB (`DOCUMENT_BYTES`, as the mediator holds its own), with `registry::capped`. Once open, a relationship carries text (Basic Message 2.0) and each side's name (User Profile 1.0, `displayName` only), always over the pairwise (`chat.rs`): the inviter sends its name after the `ping-response` with `send_back_yours`, and a changed name goes to every contact. A contact's alias is local and wins over their name. The inbox summary (name, unread, last message) lives in the state; each conversation's history is its own sealed file, named and bound (AAD) by a hash of our pairwise (`conversation.rs`), deduplicated by message `id`, so a retried message keeps its id. While the wallet is visible and open, `live.rs` holds a WebSocket to the mediator with Pickup live delivery on: each session starts with a sync (the backlog is not pushed), pushed `delivery`s go through the same `handle`/`apply` under the same `Gate` and are acknowledged on the socket, and changes reach the interface as the `messaging-changed` event; it pings when quiet, reconnects with backoff, and stops on sign-out. `push.rs` registers the device token (FCM on Android, APNs on iOS, via `tauri-plugin-notifications`, mobile only) with `set-device-info` at every unlock and whenever a mediator is chosen, and removes it on disconnect and sign-out; the mediator's push is a visible notification whose title and text are keys (`almena_wake_title`, `almena_wake_body`) into the app's own strings in `src-tauri/push/`, and nothing runs in the wallet when it arrives. Plain HTTP only for loopback in debug builds. The protocol rules are the mediator's SPEC.md (§3 and §6). Calls (`call.rs`, `SPEC.md` §3 — this project's own specification of what wallets say to each other): `call_ice_servers` asks the wallet's own mediator for TURN credentials (its TURN 1.0, `https://almena.id/protocols/turn/1.0`) before each call, and `call_send` carries `offer`/`answer`/`hangup` (`https://almena.id/protocols/call/1.0`) over the pairwise, taking the state without the `Gate`; what arrives goes through `handle` like any message and reaches the interface as the `call-signal` event, never stored. Only `typ relay` candidates cross, either way — read from the candidate's type field, not looked for anywhere in the line — and their `raddr`/`rport` are written as `0.0.0.0`/`0` (`relay_only`), since they are the device's server-reflexive address.
- `registry.rs` — signing in to an Almena Registry portal, or linking this wallet to an account there. The portal shows `https://almena.id/w/auth?request_uri=…` (link or QR code; the same as `almena://auth?request_uri=…`, read alike); `invitation_kind` calls it `registry`, and `LinkSheet` reads the request over HTTPS (`registry_request`: the portal, the host the answer goes to, the DID it will see) before Accept posts back an `id_token` (`registry_answer`): a JWS, `EdDSA`, SIOPv2's `direct_post`, `aud` the portal, the request's `nonce`. The key is derived per registry like a pairwise — `m/5'/a'/b'/c'/n'`, `a`–`c` from a hash of the origin the request was read from (the registry's identity domain, `almena.id`, where the API serves the wallet's requests; never the `client_id` it names, which anyone serving a request can write), `n` the generation (0) — so the same words give the same DID at the same registry and two registries cannot correlate it; nothing is stored. The answer only goes to the origin the request came from, and the portal the sheet names (`client_id`) must be vouched for by it (`vouched`: the same host; one label under it when it is a registrable domain itself — `registry.almena.id` named from `almena.id`; or one label under the same parent — `registry.almena.id` beside `api.almena.id`; that domain must not be a public suffix — the `psl` crate, private section included — never `a.github.io` beside `b.github.io`, nor `x.github.io` named from `github.io`). For `sign` the sheet shows that host too. Accept answers the request `registry_request` read and kept (`Shown`), never a second read of the address. For a `sign` request, what the sheet shows must be what the document says (`told_as_it_is`: a log entry's `versionId` and `state.id`), or it is refused. A `sign` request (a tenant admin signing a did:webvh log entry of one of the tenant's identities) carries the entry and the update keys that may sign it; the sheet shows the identity, its DID (or that it is new), the version and the key, refuses when this wallet's key is not a signer, and Accept posts a Data Integrity proof (`eddsa-jcs-2022`: SHA-256 of the RFC 8785 canonical proof options, then of the entry, signed) as JSON. A document with an `@context` carries it into the proof options. The kinds of `sign` are `did_log_entry`, `credential` and `status_list` (`SIGN_KINDS`); publishing an issuer, verifier or mediator in the registry asks nothing of the wallet. Same transport rules as a mediator (HTTPS; loopback HTTP in a debug build, which on a computer also trusts the system's roots — `rustls-native-certs` in `mediator::tls` — so the dev Caddy's `https://almena.id` is reachable; a release build trusts the Mozilla roots alone). **Applying for a credential** to one of the registry's issuers uses the same channel with three more purposes, each naming the issuer: `pair` (an `id_token`), `present` (an OpenID4VP request with a DCQL query, answered from the credentials held — see below) and `submit` (a JWS with the application's id and the digest of its content). Their key is the issuer's own: derived from the registry's origin and the issuer's DID together (`identity_for`), the same for pairing and submitting, different per issuer. `applies_as_it_says` refuses an application request that names no issuer, a `submit` whose content is for another issuer or whose digest (SHA-256 of the content's JCS) is not the one stated — so the answers the sheet shows are what is signed — and a sign-in that names an issuer; submitting with another key than the one paired is `registry_not_the_holder`. **Issuing**: the issuer's signer signs an application's credential as a `sign` request of kind `credential` — an SD-JWT VC's header, payload and disclosures; `told_as_it_is` requires the issuer's DID as `iss` and in the `kid` with one of the signers, the `exp` the sheet shows, every disclosure listed in `_sd` (`disclosed`) and nothing in the header or payload beyond what the API's `issuance.document` writes (`nothing_unshown`), the sheet shows each claim, the type (`vct`) and the holder (`cnf.kid`), and Accept posts `{jws}` signed over that header and payload (`compact`). The holder takes it with `purpose: receive` (`receive`): an `id_token` by the key paired with that issuer, answered with the credential, which `credentials.rs` reads — bound (`cnf.kid`) to that key, from that issuer, every disclosure listed — and `issuers.rs` verifies: its JWS signed by a key the issuer's DID document lists under `assertionMethod` (the document resolved, before the registry is answered, by walking the issuer's `did:webvh` log from its first entry — `webvh.rs`: SCID, hash chain, `eddsa-jcs-2022` proofs by the update keys in force, pre-rotation, no deactivation, witnesses refused; otherwise `registry_issuer_unverified`) — and keeps sealed under the seed (`credentials.json`, cleared with the messaging state), with the `scope` its key is derived from; Home lists them (`credentials_list`, see `src/screens/HomeTab.tsx` below), each removable for good from its detail after a second confirmation (`credentials_remove`), and checks each one's status (`credentials_check`, `status.rs`): its issuer's IETF Token Status List, fetched from the `status.status_list.uri` the credential names, after checking the credential is still signed by a key its issuer lists (else `signature`), and believed only if it is the issuer's by the same rule (`issuers.rs`), `sub` is that URI and `exp`, if any, is ahead. The status (valid, suspended, revoked) is kept with the credential (`checked`): an unreachable list keeps the last one known, an untrusted one leaves none. A credential known to be suspended or revoked, or no longer signed by a key its issuer lists, is never offered in a presentation. **Presenting** (`presentation.rs`): for each credential set of the request's DCQL query, every held, still valid SD-JWT VC that answers one of its options (format and a `vct` the query names) is offered (`offers`), the first by default; where several would do, the sheet lets the holder pick (`LinkSheet`, `pickedOption`/`choiceToSend` in `src/links.ts`) and Accept sends `choice` (set → credential id), which must be among what was offered (`picked`). The offers are kept in `Shown` with the request when `registry_request` reads it, so Accept sends what the sheet showed and works nothing out again. Only the disclosures of the claims the query asks for are sent, each presentation ending with a key-binding JWT (`kb+jwt`: `iat`, `aud` the portal, `nonce`, `sd_hash`) by the key derived again from the credential's `scope`. The sheet lists each credential and the claims that would go, says when a required one is missing; with nothing to present Accept is disabled (`registry_nothing_to_present`). Only `dc+sd-jwt` is answered. Every presentation the registry took is written down (`presented.rs`: sealed like the credentials, `presented.json`, AAD `almena-wallet/presented/1`, newest 500, cleared with the messaging state, carried in a backup): when, to whom (name and DID, whether the verifier was checked and its domains), through which portal, and which credentials with the **names** of the claims sent; `presented_list` feeds the Presented section of `CredentialScreen` (`src/presented.ts`). **A verifier asking** (`purpose: verify`, the registry's `verifications`): the request names the verifier (DID, name) and a DCQL query and nothing of an application (`applies_as_it_says`). Before the sheet shows it the wallet checks the verifier on its own (`issuers::vouch`): its DID must be a `did:webvh` on the host the request was read from, its log must resolve (so it is published), its document's `controller` must be a `did:webvh` of the same host whose log resolves too — those logs are signed by the tenant's own update keys, which the registry does not hold —, and the tenant's `LinkedDomains` are what the sheet says about who it is (`verified`, `tenant`, `domains`). The name is in no signed document and stays the registry's word; an unverified verifier is said so on the sheet (`verifierUnverified`, `verifierUnverifiedNote`), not refused. Accept answers `{vp_token}` exactly as `present` does (key binding for `client_id`, the registry portal — the verifier's DID as audience needs the API to accept it). Every JSON body read from a registry is capped at 1 MiB (`capped`, `BODY_BYTES`), DID logs and status lists at 4 MiB (`issuers::get`), and ed25519 signatures are checked with `verify_strict`. **Notices from the issuer**: pairing also opens a relationship with the issuer when there is a mediator (`messaging::issuer_channel`): the pairwise for the issuer's DID, registered with the mediator, its counterparty the issuer's `did:web` name (what messaging resolves), named as the issuer, open from the start; its DID goes in the pairing `id_token` as `didcomm`. The issuer then writes how the application stands (`https://almena.id/protocols/application/1.0/status`, `messaging/notice.rs`: accepted, rejected or issued, with its note and, issued, a `collect` address), which joins that conversation as an entry with a `notice` the interface words in its language. **Issuers send no notices for now**: the API held the issuer's messaging key, which went with the vault, so pairing and collecting remain but nothing arrives. The interface says so where a notice would be expected — the submit sheet (`submitCollect`) and Home's empty hint: come back to catalog.almena.id to see how it stands and collect the credential. Collect (`registry_collect`) posts an `id_token` by the key paired with that issuer, for the `collect` address, the application's id as nonce, and gets back the link (`deep_link`, https) of a `receive` request on the same registry, which goes to `LinkSheet` like any link. To try it from the portal on macOS, `task build:debug` and open that bundle: `task dev` receives no links. Against a local registry: `REGISTRY_DID_URL=http://localhost:8000 task dev` in `../api`, then `cargo test registry -- --ignored`.
- Plugins per platform (`src-tauri/src/lib.rs`): `single-instance`, `window-state`, `autostart`, `notification` and the system tray on a computer (`notification`, `src-tauri/src/notify.rs`: a message that arrives by live delivery while the window is not focused becomes a system notification, saying as much as Profile → Notifications chose — everything, the sender, or nothing identifying (`src/notify.ts`, kept like the other device preferences and handed to Rust with the words in the interface's language); not on a phone, where the push plugin, a fork of this one, takes the same native symbols and push announces what arrives in the background) (`autostart`: a switch in Profile → Security, desktop only (`src/autostart.ts`); the login item — a LaunchAgent on macOS — starts the wallet with `--minimized`, and the window is minimised on `RunEvent::Ready`, since in `setup` it is not on screen yet; it starts locked, so nothing is received until it is unlocked) (`tray.rs`: closing the window hides it while the tray is up — live delivery keeps running — the left click and the macOS Dock bring it back, the menu's entries, named by the front end in its language (`src/tray.ts`), open the window and quit; `window.rs` hides and shows the window, emits `window-shown` so the auto-lock is checked on return, and puts a restored window on a screen that exists; the glyphs come from `assets/branding/tray` via `task icons`); `barcode-scanner` on a phone or tablet only, where the Scan QR tab appears (`platform_info` says so, `src/platform.ts`); `deep-link` everywhere, for `almena://` — the scheme the wallet's own invitations are written with — and on a phone for `https://almena.id/w/…` too (`tauri.conf.json`'s second mobile entry, `appLink`: the plugin writes the iOS Associated Domain `applinks:almena.id` and Android's `autoVerify` intent filter at every build; `push/ios/wallet_iOS.entitlements` carries the domain as well, since `push/sync.sh` copies it over the generated one). That is the form the API hands out (`deep_link`; `scheme_link` is the `almena://` one): only an app `almena.id` names in its `/.well-known/apple-app-site-association` and `assetlinks.json` can claim it. `src-tauri/src/links.rs` (`scheme_form`) reads it as the `almena://` link it stands for — that host, no port or credentials, under `/w/`, nothing else — and `registry::request_uri` reads requests through it; contact and mediator invitations are read from any URL with `_oob` already. A computer keeps `almena://`. A link or a scanned code is classified by `invitation_kind` and put to the person in a confirmation sheet over the open screen (`LinkSheet`, built on the generic `ConfirmSheet`: icon, origin, title, one line, detail rows, Cancel and Accept — meant for more cases later). `link_details` gives it only what the wallet knows: for a contact invitation the card's fingerprint (an invitation carries no name), the contact it already is, or that it is this wallet's own; for a mediator, it and the current one — changing mediator from a link is refused while relationships route through the current one. Nothing is acted on until Accept, and a link that arrives while locked waits for the unlock (`src/links.ts`, `App.tsx`). The system learns the scheme from the bundle on macOS, iOS and Android, from the installer on Windows and from the `.deb`/`.rpm` on Linux; an AppImage registers itself at startup, and so does a Windows development build (`register_all`). `task dev` on macOS is not a bundle, so links do not reach it.
- Backup (`messaging/backup.rs`, Profile → Backup, `BackupSettings`): what the phrase does not bring back — the messaging state, every conversation, the credentials and the picture — in one file sealed like the files on the device (key `m/2'`, AAD `almena-wallet/backup/1`), saved and opened through the system's sheets (`tauri-plugin-dialog`, and `tauri-plugin-fs` for the paths and Android content URIs they return; only Rust calls them). Restoring merges under the messaging `Gate`: what the device holds wins, what the file adds is counted (`Restored`), and a second restore adds nothing. A file another identity sealed is `backup_not_this_identity`. The log of what was presented travels in it too (`presented`, absent from older files). **Reminder** (`src/backup.ts`, `backupDue`): when a credential arrived after the last backup made from the wallet and after the reminder was last put away, Home shows a card with Save a backup (the same export) and Not now; either quiets it until the next credential arrives. The two times are a device note in `localStorage` (`almena.backup.reminder`).
- `src/screens/onboarding/` — welcome, phrase, confirmation quiz, restore; then `PinSetup`. `App.tsx` decides between onboarding, the lock (`PinScreen`) and the tabs from `vault_status`. The phrase is written down, never copied: nothing puts it (or a PIN) on the clipboard; pasting into restore is fine. The phrase, the quiz, restore, the phrase check and `PinScreen` (so every PIN: setup, lock, change, biometrics) call `useShield` (`src/shield.ts`, counted so one screen handing over to the next keeps it up), which drives `screen_shield` (`src-tauri/src/shield.rs`): window content protection on Windows and macOS, `FLAG_SECURE` over JNI on Android, on iOS — where screenshots cannot be refused — a plain cover over the windows while the scene is not active, so the app switcher's picture holds nothing; on Linux nothing, there is no such API.
- `src/screens/HomeTab.tsx` — the first tab is where the credentials are: the greeting, then each credential held as a `CredentialCard` (`src/components/CredentialCard.tsx`: ID-1 proportions, the identity colour to its `--brand-strong` shade, guilloché arcs and the Almena mark — `BrandMark`, the mark drawn in `currentColor` — behind the words, the brand's ink; a `StatusChip` for how it stands), one under the other and two to a row on a wide window (`.screen--wide`). There is no category on a held credential, so every card wears `BadgeCheckIcon` and the word "Credential". What a card says comes from pure helpers in `src/credentials.ts`, tested in `credentials.test.ts`: `credentialName` (the type's name in the locale, its language, English, any, then its catalogue id), `issuerLabel` (name, else DID), `registryOf` (the host in `scope`), `standing` (revoked, suspended, invalid — a `signature` problem —, expired, valid, not checked, in that order) and `shown`. A card opens `CredentialScreen` on the tab's stack: the card, issuer, its DID, type, registry, dates, status with Check status, the claims, and Remove with its second confirmation. The list is held by `HomeTab`, so the detail and the list agree. Opening Home checks the statuses only when one was never read or not for ten minutes (`dueForCheck`), since Home opens at every unlock; its sync button checks them whenever asked. With nothing held, an empty wallet drawn in the identity colour (`src/components/illustrations/EmptyWallet.tsx`), the hint that credentials are asked for at catalog.almena.id, and a Scan QR button where that tab exists. Profile has no Credentials section: they are listed once, on Home.
- `src/screens/MessagesTab.tsx` — the inbox (`MessagesScreen`), a conversation (`ConversationScreen`) and its contact (`ContactScreen`, the alias), and what the "+" leads to: `NewConversationScreen` (directory search — not published yet — above the contacts). `InviteScreen` (QR from `src/qr.ts`, a dependency-free ISO 18004 encoder) and `AcceptInvitationScreen`: the invitation code is opened from the QR button at the top right of the Profile tab; an invitation is accepted from a scanned code or an `almena://` link. The third tab is Profile (`src/screens/ProfileScreen.tsx`): at the top the identity's picture and its name, shown only (`ProfileHeader`, over `Avatar`); the picture is shrunk to a 512-pixel JPEG in the interface (`src/photo.ts`) and sealed on the device by `messaging/photo.rs`, never sent. Under it a menu of sections in `src/screens/settings/`, each a screen of its own, the shape of the previous Almena ID wallet's settings: Profile (where the picture and the name are changed: `PhotoEditor`, `ProfileCard`), Appearance (identity colour, light/dark and the language: System — the default —, English, Español, each named in itself from its own catalogue; `src/i18n/locales.ts`, `resolveLocale` and `storedLanguage`, kept in `localStorage` as `almena.language` and held by `I18nProvider`, so it applies at once, tray and notification words included), Messaging (the mediator, `MediatorCard`) and Security (change the PIN — `PinChange` —, biometrics — `PinConfirm` —, auto-lock after 1, 5 or 10 minutes of no use, where the record is kept, check the recovery phrase, sign out). Auto-lock (`src/autolock.ts`, `src/lock.ts`) drops the identity from memory rather than hiding it; the clock counts across time spent in the background and is checked when the wallet is seen again (`idleLeft`, the one sum the timer and the return both ask). A section is listed only once there is something in it. Messages arrive live while the wallet is visible (`src/live.ts` follows `visibilitychange`); screens also sync on opening and from their sync button. In the background the mediator notifies instead (`src/push.ts`).
- Calls — `src/call.ts` runs them: one `RTCPeerConnection` with `iceTransportPolicy: "relay"`, candidates gathered before each description is sent (no trickle), one call at a time, both-calling-at-once settled by the lower call id, 45 s of ringing. `CallScreen` sits over everything while there is one; the phone and camera buttons are in the conversation's header, and absent where the webview has no WebRTC (some WebKitGTK builds). During a call live delivery stays on in the background and the auto-lock clock is held. Microphone and camera are declared in `src-tauri/Info.plist` (macOS, merged by Tauri), `Info.ios.plist`, the Android manifest and, for signed macOS builds, the entitlements the Taskfile writes. An `offer` goes with `Urgency::Call` on its `forward` (`call_send` → `contacts::send_with`), and the callee's mediator rings a closed wallet: `src-tauri/plugins/call` (this repository's own plugin) takes it — on Android a data-only FCM push to its `CallMessagingService`, declared ahead of the notifications plugin's and passing it everything else, shown as a full-screen CallStyle notification (`CallRinger`: Answer, Decline, 45 s, over the lock screen); on iOS a PushKit VoIP push reported to CallKit at once, whose token goes to the mediator as `voip_device_token` (`push.rs`). Answering or opening from it reaches `src/ring.ts`; the lock screens say somebody is calling, and once unlocked the offer is answered when it arrives (`call.ts`), and the ringing is settled (`settle`) then or after 60 s. Until a mediator release carries `Urgency`, `.cargo/config.toml` (ignored) patches `almena-didcomm` onto `../mediator`.
- `src-tauri/gen/android`, `src-tauri/gen/apple` — native projects from `tauri android|ios init`; regenerated, so settings that must survive live in `src-tauri/Info.ios.plist`, `src-tauri/PrivacyInfo.xcprivacy` (the iOS privacy manifest), `src-tauri/push/` (applied by `push/sync.sh`, which also adds the privacy manifest, which the init tasks run; it patches the Xcode project instead of running xcodegen, whose output differs from Tauri's) and the Taskfile. `google-services.json` is the publisher's and is not committed.
- `assets/branding/` — source artwork; `task icons` regenerates `src-tauri/icons` and `public/brand`. Android launcher icons under `src-tauri/icons/android` are hand-drawn.
- Navigation: the four tabs are `App.tsx`'s `route`; inside a tab, screens are a stack (`src/nav.ts`, `useStack`: push, pop, replace; the first screen is never popped), so a way back returns to whatever led there — `HomeTab` (a credential's detail), `MessagesTab` and `ProfileScreen` (its sections and the mediator, PIN, device and invitation screens) use it. The device's preferences (identity colour, light/dark, auto-lock, notification privacy) are applied once at the root (the language by `I18nProvider`, above it, read through `useI18n`) and read through a context (`src/preferences.tsx`, `usePreferences`), not passed down.
- Back: every screen's back arrow is `BackButton`, which also offers it to Android's back button and gesture while it is on screen (`src/back.ts`, Tauri's `onBackButtonPress`, held only while there is somewhere to go back to); an open `ConfirmSheet` takes it as Cancel.
- The webview runs under a strict CSP (`tauri.conf.json`: `'self'`, `ipc:`, `data:`/`blob:` for pictures, fonts and call media); `task dev` has none (`devCsp: null`), because Vite injects inline scripts.
- `src/styles/global.css` — the only place a colour is written; palettes keyed by `data-theme` and `data-accent` on the root. Each palette carries `--brand-strong` (the far corner of a credential's card) beside `--brand`, because `color-mix` is younger than the webviews; a status chip's states are `--state-*` on `--chip-bg`, the same in both themes.
- The identity colour is the person's choice, in Profile → Appearance (`src/appearance.ts`, `data-accent` on the root picks the palette in `global.css`): orange `#eb7229` (the default), blue `#2563eb`, red `#e0413a`, yellow `#f2b705`, green `#1f9d55`, cyan `#3fe0ff`, magenta `#d63384`, teal `#0fa3a3` — every portal's colour.
- Typefaces, as in the portals, bundled with the app (it works offline) from Fontsource packages imported in `src/main.tsx`: Chakra Petch (`--font-brand`: headings), Inter (`--font-sans`: the interface), JetBrains Mono (`--font-mono`: DIDs, the phrase, codes). Never load them from the network.

The look follows the previous Almena ID wallet (github.com/almena-id/wallet, branch `develop`).

## Rules

- Everything is written in English.
- The app is meant for the App Store and Google Play: a change that adds a permission, sends data off the device, or changes how the identity is removed must still meet their rules, and updates the list in `docs/store-publishing.md` (which links the guidelines, privacy declarations and agreements). Follow Apple's HIG and Material Design where the interface is platform-specific.
- User-facing text is translatable: English (`en`) is the source language, Spanish (`es`) the first translation. No hard-coded user-facing strings.
- Tasks live in `Taskfile.yml` (`task --list`). `build:macos` (development signing, for Touch ID) and `release:macos` (Developer ID, notarized, stapled) take their identity, profile and notary key from `.env.local` under names Tauri does not read (`MACOS_*`, `NOTARY_*`), so a plain `task build` never signs or notarizes; they write `src-tauri/.signing/` per build (ignored). Releases are `.github/workflows/release.yml` (every merge into `main`; the macOS job runs `task release:macos`, so keep that task working unattended) — see `docs/releasing.md`. Before finishing a change: `task check` — `tsc`, ESLint (`eslint.config.js`: TypeScript's recommended rules and the two classic hook rules), Vitest (`src/**/*.test.ts`, no DOM: screens are tested through the pure helpers they draw from, and modules that reach Tauri with `vi.mock` — `call.test.ts` drives `calls` through a mocked `call-signal`), rustfmt, clippy and the Rust tests — and `task check:mobile` when Rust changed. `.github/workflows/check.yml` runs the same on every pull request, plus the Android and iOS `cargo check`.
- Against a local mediator: in `../mediator`, `ALMENA_PUBLIC_URL=http://localhost:8080 task dev:memory`; (add `ALMENA_RATE_LIMIT=0` for repeated test runs); then `cargo test -- --ignored` in `src-tauri`, or paste `http://localhost:8080` (or its `/oob?_oob=…` link) in Settings → Mediator. The iOS simulator reaches the host's `localhost`.
