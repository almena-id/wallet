# Almena Wallet — notes for contributors and agents

The user's app for Almena Network, a decentralised messaging platform based on DIDComm Messaging v2.0
(https://identity.foundation/didcomm-messaging/spec/v2.0/). It talks to an Almena mediator (`../mediator`).

This project is independent: it has its own tooling and shares nothing with `../mediator` except the protocol.

## Layout

- `src/` — React + TypeScript front end (Vite). Package manager: pnpm.
- `src-tauri/` — Tauri v2 Rust side (`wallet_lib`).
  - `identity/`: BIP-39 phrase → seed → SLIP-0010 `m/0'` → ed25519 `did:key`. The derivation is frozen and pinned by test vectors; changing it makes existing phrases open a different identity. The seed is held in memory while the wallet is open and never crosses to the front end.
  - `vault/`: the seed on the device between launches — a versioned record (Argon2id + XChaCha20-Poly1305, 10 PIN attempts) kept in the platform's secret store, or a private file on Android. Every PIN check goes through `attempt`. Changing the PIN rewraps the data key and leaves the seed as it was. Biometrics put a copy of the data key in a store the system holds behind its own presence check (`require-user-presence`): the protected keychain on iOS, the data protection keychain on a signed macOS build with a sensor (probed at startup, `presence.rs`); arming costs the PIN and is proven by reading the key back. Windows, Linux and Android do not offer it. **On an iPhone with a passcode there is no PIN**: the record (version 2) carries no PIN wrap and the data key is kept with `userPresence` + `WhenPasscodeSetThisDeviceOnly` (`store::set_device_lock`) — Face ID first, then the passcode; the lock screen is `DeviceLockScreen`. A PIN is chosen only where the iPhone has no passcode, and a PIN wallet moves over on its next opening once there is one. Removing the passcode deletes the key, and the phrase is the way back.
  - `messaging/`: the mediation with a DIDComm mediator and the relationships through it, on `almena-didcomm` (git dependency on `../mediator`'s repository, pinned to a tag). Every DID is a `did:peer:2` derived from the seed whose service routes through the mediator (`peer.rs`): the inbox (`m/1'`, keys the mediation, never shared), the contact card (`m/4'`, named by the wallet's OOB invitation) and one pairwise per counterparty (`m/3'/…`, from a hash of the counterparty's DID). DIDs other than the inbox are registered with a possession proof. A relationship opens with a Trust Ping from the accepter's pairwise to the card, answered from a new pairwise with `from_prior` signed by the card (`contacts.rs`). The mediator and the relationships are sealed under `m/2'` (`state.rs`); no secret key is stored. Requests to the mediator are authcrypted with `return_route: "all"`, and each operation re-sends the idempotent `mediate-request` first. Once open, a relationship carries text (Basic Message 2.0) and each side's name (User Profile 1.0, `displayName` only), always over the pairwise (`chat.rs`): the inviter sends its name after the `ping-response` with `send_back_yours`, and a changed name goes to every contact. A contact's alias is local and wins over their name. The inbox summary (name, unread, last message) lives in the state; each conversation's history is its own sealed file, named and bound (AAD) by a hash of our pairwise (`conversation.rs`), deduplicated by message `id`, so a retried message keeps its id. While the wallet is visible and open, `live.rs` holds a WebSocket to the mediator with Pickup live delivery on: each session starts with a sync (the backlog is not pushed), pushed `delivery`s go through the same `handle`/`apply` under the same `Gate` and are acknowledged on the socket, and changes reach the interface as the `messaging-changed` event; it pings when quiet, reconnects with backoff, and stops on sign-out. `push.rs` registers the device token (FCM on Android, APNs on iOS, via `tauri-plugin-notifications`, mobile only) with `set-device-info` at every unlock and whenever a mediator is chosen, and removes it on disconnect and sign-out; the mediator's push is a visible notification whose title and text are keys (`almena_wake_title`, `almena_wake_body`) into the app's own strings in `src-tauri/push/`, and nothing runs in the wallet when it arrives. Plain HTTP only for loopback in debug builds. The protocol rules are the mediator's `docs/didcomm.md` §4–5. Calls (`call.rs`, `SPEC.md` §3 — this project's own specification of what wallets say to each other): `call_ice_servers` asks the wallet's own mediator for TURN credentials (its TURN 1.0, `https://almena.id/protocols/turn/1.0`) before each call, and `call_send` carries `offer`/`answer`/`hangup` (`https://almena.id/protocols/call/1.0`) over the pairwise, taking the state without the `Gate`; what arrives goes through `handle` like any message and reaches the interface as the `call-signal` event, never stored. Only `typ relay` candidates cross, either way.
- `registry.rs` — signing in to an Almena Registry portal, or linking this wallet to an account there. The portal shows `almena://auth?request_uri=…` (link or QR code); `invitation_kind` calls it `registry`, and `LinkSheet` reads the request over HTTPS (`registry_request`: the portal, the host the answer goes to, the DID it will see) before Accept posts back an `id_token` (`registry_answer`): a JWS, `EdDSA`, SIOPv2's `direct_post`, `aud` the portal, the request's `nonce`. The key is derived per registry like a pairwise — `m/5'/a'/b'/c'/n'`, `a`–`c` from a hash of the origin the request was read from (the registry's API, never the `client_id` it names, which anyone serving a request can write), `n` the generation (0) — so the same words give the same DID at the same registry and two registries cannot correlate it; nothing is stored. The answer only goes to the origin the request came from, and the portal the sheet names (`client_id`) must be vouched for by it (`vouched`: the same host, or one label under the same parent with a dot of its own — `registry.almena.id` beside `api.almena.id`). For `sign` the sheet shows that host too. Accept answers the request `registry_request` read and kept (`Shown`), never a second read of the address. For a `sign` request, what the sheet shows must be what the document says (`told_as_it_is`: a log entry's `versionId` and `state.id`; an endorsement's subject, name, issuer, `validUntil` and the presentation's holder), or it is refused. A `sign` request (a tenant admin signing a did:webvh log entry of one of the tenant's identities) carries the entry and the update keys that may sign it; the sheet shows the identity, its DID (or that it is new), the version and the key, refuses when this wallet's key is not a signer, and Accept posts a Data Integrity proof (`eddsa-jcs-2022`: SHA-256 of the RFC 8785 canonical proof options, then of the entry, signed) as JSON. An `endorsement` (a tenant admin publishing one of its issuers, verifiers or mediators) is two signatures in one approval: the tenant's membership credential, then the item's `whois.vp` with that credential inside — both with the key named under the tenant's DID, the second for `authentication` as the item's controller; a document with an `@context` carries it into the proof options. Same transport rules as a mediator (HTTPS; loopback HTTP in a debug build, which on a computer also trusts the system's roots — `rustls-native-certs` in `mediator::tls` — so the dev Caddy's `https://api.almena.id` is reachable; a release build trusts the Mozilla roots alone). **Applying for a credential** to one of the registry's issuers uses the same channel with three more purposes, each naming the issuer: `pair` (an `id_token`), `present` (an OpenID4VP request with a DCQL query, answered from the credentials held — see below) and `submit` (a JWS with the application's id and the digest of its content). Their key is the issuer's own: derived from the registry's origin and the issuer's DID together (`identity_for`), the same for pairing and submitting, different per issuer. `applies_as_it_says` refuses an application request that names no issuer, a `submit` whose content is for another issuer or whose digest (SHA-256 of the content's JCS) is not the one stated — so the answers the sheet shows are what is signed — and a sign-in that names an issuer; submitting with another key than the one paired is `registry_not_the_holder`. **Issuing**: the issuer's signer signs an application's credential as a `sign` request of kind `credential` — an SD-JWT VC's header, payload and disclosures; `told_as_it_is` requires the issuer's DID as `iss` and in the `kid` with one of the signers, the `exp` the sheet shows and every disclosure listed in `_sd` (`disclosed`), the sheet shows each claim, and Accept posts `{jws}` signed over that header and payload (`compact`). The holder takes it with `purpose: receive` (`receive`): an `id_token` by the key paired with that issuer, answered with the credential, which `credentials.rs` reads — bound (`cnf.kid`) to that key, from that issuer, every disclosure listed — and keeps sealed under the seed (`credentials.json`, cleared with the messaging state), with the `scope` its key is derived from; Profile → Credentials lists them (`CredentialsSettings`, `credentials_list`). **Presenting** (`presentation.rs`): for each credential set of the request's DCQL query, the first option a held, still valid SD-JWT VC answers (format and a `vct` the query names); only the disclosures of the claims the query asks for are sent, each presentation ending with a key-binding JWT (`kb+jwt`: `iat`, `aud` the portal, `nonce`, `sd_hash`) by the key derived again from the credential's `scope`. The sheet lists each credential and the claims that would go, says when a required one is missing, and Accept sends that same choice as `{vp_token}`; with nothing to present Accept is disabled (`registry_nothing_to_present`). Only `dc+sd-jwt` is answered. To try it from the portal on macOS, `task build:debug` and open that bundle: `task dev` receives no links. Against a local registry: `REGISTRY_PUBLIC_URL=http://localhost:8000 task dev` in `../api`, then `cargo test registry -- --ignored`.
- Plugins per platform (`src-tauri/src/lib.rs`): `single-instance`, `window-state`, `autostart`, `notification` and the system tray on a computer (`notification`, `src-tauri/src/notify.rs`: a message that arrives by live delivery while the window is not focused becomes a system notification, saying as much as Profile → Notifications chose — everything, the sender, or nothing identifying (`src/notify.ts`, kept like the other device preferences and handed to Rust with the words in the interface's language); not on a phone, where the push plugin, a fork of this one, takes the same native symbols and push announces what arrives in the background) (`autostart`: a switch in Profile → Security, desktop only (`src/autostart.ts`); the login item — a LaunchAgent on macOS — starts the wallet with `--minimized`, and the window is minimised on `RunEvent::Ready`, since in `setup` it is not on screen yet; it starts locked, so nothing is received until it is unlocked) (`tray.rs`: closing the window hides it while the tray is up — live delivery keeps running — the left click and the macOS Dock bring it back, the menu's one entry, named by the front end in its language (`src/tray.ts`), quits; `window.rs` hides and shows the window, emits `window-shown` so the auto-lock is checked on return, and puts a restored window on a screen that exists; the glyphs come from `assets/branding/tray` via `task icons`); `barcode-scanner` on a phone or tablet only, where the Scan QR tab appears (`platform_info` says so, `src/platform.ts`); `deep-link` everywhere, for `almena://` — the scheme the wallet's own invitations are written with. A link or a scanned code is classified by `invitation_kind` and put to the person in a confirmation sheet over the open screen (`LinkSheet`, built on the generic `ConfirmSheet`: icon, origin, title, one line, detail rows, Cancel and Accept — meant for more cases later). `link_details` gives it only what the wallet knows: for a contact invitation the card's fingerprint (an invitation carries no name), the contact it already is, or that it is this wallet's own; for a mediator, it and the current one — changing mediator from a link is refused while relationships route through the current one. Nothing is acted on until Accept, and a link that arrives while locked waits for the unlock (`src/links.ts`, `App.tsx`). The system learns the scheme from the bundle on macOS, iOS and Android, from the installer on Windows and from the `.deb`/`.rpm` on Linux; an AppImage registers itself at startup, and so does a Windows development build (`register_all`). `task dev` on macOS is not a bundle, so links do not reach it.
- `src/screens/onboarding/` — welcome, phrase, confirmation quiz, restore; then `PinSetup`. `App.tsx` decides between onboarding, the lock (`PinScreen`) and the tabs from `vault_status`.
- `src/screens/MessagesTab.tsx` — the inbox (`MessagesScreen`), a conversation (`ConversationScreen`) and its contact (`ContactScreen`, the alias), and what the "+" leads to: `NewConversationScreen` (directory search — not published yet — above the contacts). `InviteScreen` (QR from `src/qr.ts`, a dependency-free ISO 18004 encoder) and `AcceptInvitationScreen`: the invitation code is opened from the QR button at the top right of the Profile tab; an invitation is accepted from a scanned code or an `almena://` link. The third tab is Profile (`src/screens/ProfileScreen.tsx`): at the top the identity's picture and its name, shown only (`ProfileHeader`, over `Avatar`); the picture is shrunk to a 512-pixel JPEG in the interface (`src/photo.ts`) and sealed on the device by `messaging/photo.rs`, never sent. Under it a menu of sections in `src/screens/settings/`, each a screen of its own, the shape of the previous Almena ID wallet's settings: Profile (where the picture and the name are changed: `PhotoEditor`, `ProfileCard`), Appearance (identity colour and light/dark), Messaging (the mediator, `MediatorCard`) and Security (change the PIN — `PinChange` —, biometrics — `PinConfirm` —, auto-lock after 1, 5 or 10 minutes of no use, where the record is kept, sign out). Auto-lock (`src/autolock.ts`, `src/lock.ts`) drops the identity from memory rather than hiding it; the clock counts across time spent in the background and is checked when the wallet is seen again. A section is listed only once there is something in it. Messages arrive live while the wallet is visible (`src/live.ts` follows `visibilitychange`); screens also sync on opening and from their sync button. In the background the mediator notifies instead (`src/push.ts`).
- Calls — `src/call.ts` runs them: one `RTCPeerConnection` with `iceTransportPolicy: "relay"`, candidates gathered before each description is sent (no trickle), one call at a time, both-calling-at-once settled by the lower call id, 45 s of ringing. `CallScreen` sits over everything while there is one; the phone and camera buttons are in the conversation's header, and absent where the webview has no WebRTC (some WebKitGTK builds). During a call live delivery stays on in the background and the auto-lock clock is held. Microphone and camera are declared in `src-tauri/Info.plist` (macOS, merged by Tauri), `Info.ios.plist`, the Android manifest and, for signed macOS builds, the entitlements the Taskfile writes. Incoming calls ring only on a wallet receiving live; there is no wake-up for them yet.
- `src-tauri/gen/android`, `src-tauri/gen/apple` — native projects from `tauri android|ios init`; regenerated, so settings that must survive live in `src-tauri/Info.ios.plist`, `src-tauri/push/` (applied by `push/sync.sh`, which the init tasks run; it patches the Xcode project instead of running xcodegen, whose output differs from Tauri's) and the Taskfile. `google-services.json` is the publisher's and is not committed.
- `assets/branding/` — source artwork; `task icons` regenerates `src-tauri/icons` and `public/brand`. Android launcher icons under `src-tauri/icons/android` are hand-drawn.
- `src/styles/global.css` — the only place a colour is written; palettes keyed by `data-theme` and `data-accent` on the root.
- The identity colour is the person's choice, in Profile → Appearance (`src/appearance.ts`, `data-accent` on the root picks the palette in `global.css`): orange `#eb7229` (the default), blue `#2563eb`, red `#e0413a`, yellow `#f2b705`, green `#1f9d55`, cyan `#3fe0ff`, magenta `#d63384`, teal `#0fa3a3` — every portal's colour.
- Typefaces, as in the portals, bundled with the app (it works offline) from Fontsource packages imported in `src/main.tsx`: Chakra Petch (`--font-brand`: headings), Inter (`--font-sans`: the interface), JetBrains Mono (`--font-mono`: DIDs, the phrase, codes). Never load them from the network.

The look follows the previous Almena ID wallet (github.com/almena-id/wallet, branch `develop`).

## Rules

- Everything is written in English.
- The app is meant for the App Store and Google Play: a change that adds a permission, sends data off the device, or changes how the identity is removed must still meet their rules, and updates the list in `docs/store-publishing.md` (which links the guidelines, privacy declarations and agreements). Follow Apple's HIG and Material Design where the interface is platform-specific.
- User-facing text is translatable: English (`en`) is the source language, Spanish (`es`) the first translation. No hard-coded user-facing strings.
- Tasks live in `Taskfile.yml` (`task --list`). `build:macos` (development signing, for Touch ID) and `release:macos` (Developer ID, notarized, stapled) take their identity, profile and notary key from `.env.local` under names Tauri does not read (`MACOS_*`, `NOTARY_*`), so a plain `task build` never signs or notarizes; they write `src-tauri/.signing/` per build (ignored). Before finishing a change: `task check` (and `task check:mobile` when Rust changed).
- Against a local mediator: in `../mediator`, `ALMENA_PUBLIC_URL=http://localhost:8080 task dev:memory`; (add `ALMENA_RATE_LIMIT=0` for repeated test runs); then `cargo test -- --ignored` in `src-tauri`, or paste `http://localhost:8080` (or its `/oob?_oob=…` link) in Settings → Mediator. The iOS simulator reaches the host's `localhost`.
