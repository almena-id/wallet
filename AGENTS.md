# Almena Wallet — notes for contributors and agents

The user's app for Almena ID, a decentralised messaging platform based on DIDComm Messaging v2.0
(https://identity.foundation/didcomm-messaging/spec/v2.0/). It talks to an Almena mediator (`../mediator`).

This project is independent: it has its own tooling and shares nothing with `../mediator` except the protocol.

## Layout

- `src/` — React + TypeScript front end (Vite). Package manager: pnpm.
- `src-tauri/` — Tauri v2 Rust side (`wallet_lib`).
  - `identity/`: BIP-39 phrase → seed → SLIP-0010 `m/0'` → ed25519 `did:key`. The derivation is frozen and pinned by test vectors; changing it makes existing phrases open a different identity. The seed is held in memory while the wallet is open and never crosses to the front end. The phrase is never kept, so it cannot be shown again; Profile → Security → Check your recovery phrase (`PhraseCheckScreen`, `src/phraseCheck.ts`) asks for the PIN — or biometrics, or on an iPhone without one its own lock — through `vault_confirm` (`attempt`, or `presence::open` with the key proven against the record), which marks `Held` confirmed for five minutes (`CONFIRMED_FOR`, dropped with the seed and on every `adopt`); only then does `identity_check_phrase` read the typed words as a restore does (`phrase::read`, `seed_of`), compare their seed with the open one in constant time (`subtle`) and answer yes or no (`identity_unconfirmed` without it). The words are neither stored nor logged; a typed phrase is lower-cased and NFKD-normalised as the wordlists are written (`unicode-normalization`, so composed accents read), straight into memory that is wiped. `identity_create` and `identity_restore` refuse while anything is where the record goes (`vault::occupied`, the rule `vault_create` keeps too; `identity_exists`): an identity put in memory behind the lock screen would be open without its PIN.
  - `vault/`: the seed on the device between launches — a versioned record (Argon2id + XChaCha20-Poly1305, 10 PIN attempts) kept in the platform's secret store, or on Android a private file sealed again (AES-256-GCM, `almena-keystore/1` prefix) under a key the Android Keystore generates and never releases — StrongBox where there is one, the TEE otherwise — by this repository's own plugin, `src-tauri/plugins/keystore` (Rust in `src/`, Kotlin in `android/`, pulled into the Gradle project by tauri-build however often `gen/android` is regenerated); a record the Keystore would not seal when it was written is sealed the first time it is read and the Keystore will, and one the Keystore cannot open (a restore from a backup, which never carries the key) reads as unreadable, so the phrase is the way back. The record is left out of the system's backups and device transfers (`src-tauri/backup/`, put into the manifest by `push/sync.sh`): it would open nowhere else. Security shows which (`keystore`). Every PIN check goes through `attempt`. A write the platform's store refuses goes to the file only once the store's older copy is gone (`store::write`): reading prefers the store, and a copy it would not let go of would undo every count of wrong PINs, so that fails the write. A record without a PIN is read only where one is written (`held_here`: an iPhone with a passcode); anywhere else it is unreadable. **How short a PIN may be follows where the record is kept** (`store::hardware_bound`, `vault::shortest`): four or six digits where hardware keeps it on the device — the iOS Keychain item (`this-device-only`) and the file sealed under the Android Keystore —, six everywhere a process of the same user could copy it off and try every PIN offline: Windows, Linux, macOS (the record is in the file keychain on every build, signed or not; only the device key reaches the data protection keychain) and an Android file the Keystore would not seal — asked before the first PIN (`store::next_home` has the Keystore seal a probe, and `minDigits` follows), and a four-digit record that landed in a file anyway is taken back as `vault_pin_too_short`. A new or changed PIN shorter than that is `vault_pin_too_short`; `vault_status` says `minDigits` and, for a record holding a shorter one, `lengthen`, and `App.tsx` then puts `PinChange` (no way back, the digits just typed handed over as `known`) between the unlock and the tabs until it is six. `vault_destroy` removes nothing unless told `confirm: "sign-out"` (`vault_unconfirmed`), which only the sign-out screen sends. Changing the PIN rewraps the data key and leaves the seed as it was. Biometrics put a copy of the data key where the system holds it behind its own presence check, one `Keeper` per platform in `presence.rs` (`presence/android.rs`, `presence/hello.rs`) with the rules shared and tested once there (`arm`, `disarm`, `open`, `changed`), so the front end sees only `deviceUnlock`, `deviceKey`, `deviceChanged` and which system it is (`biometrics`: `apple`, `android`, `windows`, worded by `src/biometrics.ts` — "Biometrics", "Fingerprint or face", "Windows Hello"): the protected keychain on iOS and, on a signed macOS build with a sensor (probed at startup), the data protection keychain (`require-user-presence`), where arming is proven by reading the key back; on Android a second Keystore key (`almena-vault-biometric`: AES-256-GCM, StrongBox where there is one, `setUserAuthenticationRequired` with `AUTH_BIOMETRIC_STRONG` per operation — validity -1 before API 30 —, `setInvalidatedByBiometricEnrollment`) whose cipher only a `BiometricPrompt` with a `CryptoObject` unlocks (androidx.biometric; strong biometrics, negative button "Use PIN", words handed over by the front end as `prompt`), the sealed copy in `vault.biometric` beside the record and left out of backups like it; on Windows a Windows Hello key (`KeyCredentialManager`, `almena-wallet`) signs a random 32-byte challenge — PKCS#1 v1.5, deterministic — and HKDF-SHA256 of the signature wraps the data key (XChaCha20-Poly1305), challenge and wrap kept in the Credential Manager under `hello-key`; the Hello prompt cannot be parented to the window (no HWND variant). Linux has no standard presence API and does not offer it. Arming always costs the PIN, and on Android and Windows sealing itself answers the prompt. Opening with the device's own check sets the count of wrong PINs back to nought, as the right PIN does (`forgive`). A copy the system can no longer hand back — a fingerprint or face enrolled since, Hello reset — is `deviceChanged` (asked without a prompt), `vault_device_changed` when tried; the record is disarmed then or at the next PIN opening, the lock screen says why, and the PIN opens it as ever. Signing out removes every copy (`store::clear`). **On an iPhone with a passcode there is no PIN**: the record (version 2) carries no PIN wrap and the data key is kept with `userPresence` + `WhenPasscodeSetThisDeviceOnly` (`store::set_device_lock`) — Face ID first, then the passcode; the lock screen is `DeviceLockScreen`. A PIN is chosen only where the iPhone has no passcode, and a PIN wallet moves over on its next opening once there is one. Removing the passcode deletes the key, and the phrase is the way back.
  - `messaging/`: the mediation with a DIDComm mediator and the relationships through it, on `almena-didcomm` (git dependency on `../mediator`'s repository, pinned to a commit). Every DID is a `did:peer:2` derived from the seed whose service routes through the mediator (`peer.rs`): the inbox (`m/1'/x/y/z`, keys the mediation, never shared), the contact card (`m/4'/x/y/z`, named by the wallet's OOB invitation) and one pairwise per counterparty (`m/3'/x/y/z/a/b/c`, `a/b/c` from a hash of the counterparty's DID). `x/y/z` come from a hash of the mediator's DID, so the keys themselves — not only the DID's service — differ per mediator: no two mediators, nor a relationship moved between them, ever see the same public key (`peer.rs`, `two_mediators_see_no_key_in_common`; the paths are pinned by `the_paths_are_as_documented`). DIDs other than the inbox are registered with a possession proof. A relationship opens with a Trust Ping from the accepter's pairwise to the card, answered from a new pairwise with `from_prior` signed by the card (`contacts.rs`); whoever holds the invitation may open one, but past `WELCOMES` (20) opened through the card in a day, whether or not anything was said in them, a stranger's ping is dropped (`welcomed` marks them). **Every message is acknowledged** (`handle`): one from anyone but the relationship's current pairwise — a pending one's included, since the `ping-response` with the rotation is the first thing their new pairwise sends —, any type the wallet does not speak, and a ping that cannot be answered (its pairwise is unregistered again, unless it is already a contact's) are dropped rather than left queued, because the mediator delivers the oldest first and a few left there would stop every sync. The mediations and the relationships are sealed under `m/2'` (`state.rs`); no secret key is stored. **One mediator** (decided 2026-11-11; several at once were built and taken back, to be revisited): each `Relationship` records the `mediator` its pairwise was derived for. `mediator_connect` to another mediator marks the old one `leaving`, moves every relationship to the new one (`relocate_all` → `relocate`: a pairwise at the new mediator, a `profile` message from it carrying `from_prior` signed by the old pairwise, and `previous` keeps the old one collected for `GRACE_SECS` — 30 days, the mediator's queue lifetime; `Relationship::is_for` accepts both) and keeps the old mediation in `State.mediations` only while it is collected. Sync, live delivery (one socket per mediation held, `live.rs` `run_at`) and push registration cover it too. `settle`, at every sync, retries the moves off a mediator being left, unregisters old pairwises whose grace is over and drops the old mediation once nothing goes through it. `mediator_disconnect` forgets the current mediation as before; its relationships wait, unreachable (`stranded`: on a mediator with no mediation), and `mediator_connect` and every `settle` move them to the next one like those of a mediator being left. **Room**: an Almena mediator's `mediate-grant` says `max_recipient_dids`; `ensure` returns it, `Mediation.max_dids` keeps it (refreshed at every sync), `MediatorEntry` gives `dids` (inbox + card, whether shown or not, + one per contact) and `max_dids`, and `MediatorCard` shows "Addresses: n of max" with what takes one, and warns from 90 %. A refused `add` with `reason: "limit"` is `MessagingError::MailboxFull` (`messaging_mailbox_full`, `mediator::refused`); a stranger's ping that does not fit is dropped rather than kept for every sync. Any message whose valid `from_prior` the counterparty's current DID signed moves `theirs` to its sender (`handle`), the card's rotation included; see `SPEC.md` §3. A conversation's id is a hash of the relationship's `origin`, so it survives a move. What arrives is read with `Mediator::reader`: a sender's `did:web` is fetched only when it is a relationship's counterparty, so a stranger's slow host holds nothing up (and learns nothing of when the wallet syncs); a batch is written into each conversation once (`conversation::put_all`), and a desktop notification is one per sender, their latest. Requests to the mediator are authcrypted with `return_route: "all"`, and each operation re-sends the idempotent `mediate-request` first. Its answers are read under 24 MiB (`ANSWER_BYTES`: a `delivery` of `DELIVERY_LIMIT` messages, never more than a mediation's 10 MiB queue, base64 twice over) and a `did:web` document under 1 MiB (`DOCUMENT_BYTES`, as the mediator holds its own), with `registry::capped`. Once open, a relationship carries text (Basic Message 2.0) and each side's name (User Profile 1.0, `displayName` only), always over the pairwise (`chat.rs`): the inviter sends its name after the `ping-response` with `send_back_yours`, and a changed name goes to every contact. A contact's alias is local and wins over their name. The inbox summary (name, unread, last message) lives in the state; each conversation's history is its own sealed file, named and bound (AAD) by a hash of the relationship's `origin` (`conversation.rs`), deduplicated by message `id`, so a retried message keeps its id. While the wallet is visible and open, `live.rs` holds a WebSocket to the mediator with Pickup live delivery on: each session starts with a sync (the backlog is not pushed), pushed `delivery`s go through the same `handle`/`apply` under the same `Gate` and are acknowledged on the socket, and changes reach the interface as the `messaging-changed` event; it pings when quiet, reconnects with backoff, and stops on sign-out; its messages and frames are held to `ANSWER_BYTES`, as an asked-for delivery is. `push.rs` registers the device token (FCM on Android, APNs on iOS, via `tauri-plugin-notifications`, mobile only) with `set-device-info` at every unlock and whenever a mediator is chosen, and removes it on disconnect and sign-out; the mediator's push is a visible notification whose title and text are keys (`almena_wake_title`, `almena_wake_body`) into the app's own strings in `src-tauri/push/`, and nothing runs in the wallet when it arrives. Plain HTTP only for loopback in debug builds. The protocol rules are the mediator's SPEC.md (§3 and §6); what wallets say to each other is this project's `SPEC.md`. There are no calls: voice and video calls (WebRTC over the mediator's TURN relay, rung through PushKit/CallKit and a full-screen Android notification) were removed on 2026-11-10, and a call message from an older wallet is a type the wallet does not speak.
- `registry.rs` — signing in to an Almena Registry portal, or linking this wallet to an account there. The portal shows `https://almena.id/w/auth?request_uri=…` (link or QR code; the same as `almena://auth?request_uri=…`, read alike); `invitation_kind` calls it `registry`, and `LinkSheet` reads the request over HTTPS (`registry_request`: the portal, the host the answer goes to, the DID it will see) before Accept posts back an `id_token` (`registry_answer`): a JWS, `EdDSA`, SIOPv2's `direct_post`, `aud` the portal, the request's `nonce`. The key is derived per registry like a pairwise — `m/5'/a'/b'/c'/n'`, `a`–`c` from a hash of the origin the request was read from (the registry's identity domain, `almena.id`, where the API serves the wallet's requests; never the `client_id` it names, which anyone serving a request can write), `n` the generation (0) — so the same words give the same DID at the same registry and two registries cannot correlate it; nothing is stored. The answer only goes to the origin the request came from, and the portal the sheet names (`client_id`) must be vouched for by it (`vouched`: the same host; one label under it when it is a registrable domain itself — `registry.almena.id` named from `almena.id`; or one label under the same parent — `registry.almena.id` beside `api.almena.id`; that domain must not be a public suffix — the `psl` crate, private section included — never `a.github.io` beside `b.github.io`, nor `x.github.io` named from `github.io`). For `sign` the sheet shows that host too. Accept answers the request `registry_request` read and kept (`Shown`), never a second read of the address. For a `sign` request, what the sheet shows must be what the document says (`told_as_it_is`: a log entry's `versionId` and `state.id`; "new DID" only for the first entry and the first entry only as a new DID; no parameters but `method`, `scid` and `updateKeys` — never a deactivation, witnesses or pre-rotation —, a change of `updateKeys` shown key by key with this wallet's marked, `nextSigners`), or it is refused. A `status_list` is compared with the list the issuer publishes now, read and checked as its signature (`status::published`, `changes_only`): every status the same but the one the sheet names; with none published, every other status valid, which the sheet says (`allValid`). A `sign` request (a tenant admin signing a did:webvh log entry of one of the tenant's identities) carries the entry and the update keys that may sign it; the sheet shows the identity, its DID (or that it is new), the version and the key, refuses when this wallet's key is not a signer, and Accept posts a Data Integrity proof (`eddsa-jcs-2022`: SHA-256 of the RFC 8785 canonical proof options, then of the entry, signed) as JSON. A document with an `@context` carries it into the proof options. The kinds of `sign` are `did_log_entry`, `credential` and `status_list` (`SIGN_KINDS`); publishing an issuer, verifier or mediator in the registry asks nothing of the wallet. Same transport rules as a mediator (HTTPS; loopback HTTP in a debug build, which on a computer also trusts the system's roots — `rustls-native-certs` in `mediator::tls` — so the dev Caddy's `https://almena.id` is reachable; a release build trusts the Mozilla roots alone). **Applying for a credential** to one of the registry's issuers uses the same channel with three more purposes, each naming the issuer: `pair` (an `id_token`), `present` (an OpenID4VP request with a DCQL query, answered from the credentials held — see below) and `submit` (a JWS with the application's id and the digest of its content). Their key is the issuer's own: derived from the registry's origin and the issuer's DID together (`identity_for`), the same for pairing and submitting, different per issuer. The issuer named is checked by `issuers::vouch` as a verifier is (below), and the sheet says whether it could be (`verified`, `domains`, `issuerUnverifiedNote`). `applies_as_it_says` refuses an application request that names no issuer or one that is not a `did:webvh`, a `submit` whose content is for another issuer or whose digest (SHA-256 of the content's JCS) is not the one stated — so the answers the sheet shows are what is signed — and a sign-in that names an issuer; submitting with another key than the one paired is `registry_not_the_holder`. **Issuing**: the issuer's signer signs an application's credential as a `sign` request of kind `credential` — an SD-JWT VC's header, payload and disclosures; `told_as_it_is` requires the issuer's DID as `iss` and in the `kid` with one of the signers, the `exp` the sheet shows, every disclosure listed in `_sd` (`disclosed`) and nothing in the header or payload beyond what the API's `issuance.document` writes (`nothing_unshown`), the sheet shows each claim, the type (`vct`) and the holder (`cnf.kid`), and Accept posts `{jws}` signed over that header and payload (`compact`). The holder takes it with `purpose: receive` (`receive`), only from an issuer `issuers::vouch` verified (else `registry_issuer_unverified`, and the sheet's Accept is disabled, `issuerUnverifiedReceive`): an `id_token` by the key paired with that issuer, answered with the credential, which `credentials.rs` reads — bound (`cnf.kid`) to that key, from that issuer, of the type applied for (the answer's `credential_type.id` and its `vct`, which the credential's must be), every disclosure listed — and `issuers.rs` verifies: its JWS signed by a key the issuer's DID document lists under `assertionMethod` (the document resolved, before the registry is answered, by walking the issuer's `did:webvh` log from its first entry — `webvh.rs`: SCID, hash chain, `eddsa-jcs-2022` proofs by the update keys in force, pre-rotation, no deactivation, witnesses refused; otherwise `registry_issuer_unverified`) — and keeps sealed under the seed (`credentials.json`, cleared with the messaging state), with the `scope` its key is derived from; Home lists them (`credentials_list`, see `src/screens/HomeTab.tsx` below), each removable for good from its detail after a second confirmation (`credentials_remove`), and checks each one's status (`credentials_check`, `status.rs`): its issuer's IETF Token Status List, fetched from the `status.status_list.uri` the credential names, after checking the credential is still signed by a key its issuer lists (else `signature`), and believed only if it is the issuer's by the same rule (`issuers.rs`), `sub` is that URI and `exp`, if any, is ahead. The status (valid, suspended, revoked) is kept with the credential (`checked`): an unreachable list keeps the last one known, an untrusted one leaves none, and one issued (`iat`) before the newest already read (`Checked::listed`) is not news: an old list served again cannot undo a revocation. The registry's lists carry no `exp`, so nothing bounds how old the newest one may be. A credential known to be suspended or revoked, or no longer signed by a key its issuer lists, is never offered in a presentation. **Presenting** (`presentation.rs`): for each credential set of the request's DCQL query, every held, still valid SD-JWT VC that answers one of its options (format and a `vct` the query names) is offered (`offers`), the first by default; where several would do, the sheet lets the holder pick (`LinkSheet`, `pickedOption`/`choiceToSend` in `src/links.ts`) and Accept sends `choice` (set → credential id), which must be among what was offered (`picked`). The offers are kept in `Shown` with the request when `registry_request` reads it, so Accept sends what the sheet showed and works nothing out again. Only the disclosures of the claims the query asks for are sent (`disclosing`: a claim only by a one-step path, since a disclosure is a whole claim and a path into one would send all of it; only a value among its `values`; with `claim_sets`, the first set answered whole), each presentation ending with a key-binding JWT (`kb+jwt`: `iat`, `aud` the portal, `nonce`, `sd_hash`) by the key derived again from the credential's `scope`. The sheet lists each credential and the claims that would go, says when a required one is missing; with nothing to present Accept is disabled (`registry_nothing_to_present`). Only `dc+sd-jwt` is answered. Every presentation the registry took is written down (`presented.rs`: sealed like the credentials, `presented.json`, AAD `almena-wallet/presented/1`, newest 500, cleared with the messaging state, carried in a backup): when, to whom (name and DID, whether the verifier was checked and its domains), through which portal, and which credentials with the **names** of the claims sent; `presented_list` feeds the Presented section of `CredentialScreen` (`src/presented.ts`). **A verifier asking** (`purpose: verify`, the registry's `verifications`): the request names the verifier (DID, name) and a DCQL query and nothing of an application (`applies_as_it_says`). Before the sheet shows it the wallet checks the verifier on its own (`issuers::vouch`): its DID must be a `did:webvh` on the host the request was read from, its log must resolve (so it is published), its document's `controller` must be a `did:webvh` of the same host whose log resolves too, and the last entry of the verifier's log must be signed by one of the update keys in force in the tenant's (`webvh::resolve_log`: `update_keys`, `signed_by`) — `controller` alone is the item's own word, which any tenant could write about another, while the tenant's update keys are its signers' wallets, which neither another tenant nor the registry holds (`only_the_tenants_own_signers_make_an_item_its_own`). The tenant's `LinkedDomains` are its own signed word, which the registry checked by DNS and the wallet cannot: the sheet lists them as what it states (`verifierDomains`), apart from whether it was checked (`verified`, `tenant`, `domains`). The name is in no signed document and stays the registry's word; an unverified verifier is said so on the sheet (`verifierUnverified`, `verifierUnverifiedNote`), not refused. Accept answers `{vp_token}` exactly as `present` does (key binding for `client_id`, the registry portal — the verifier's DID as audience needs the API to accept it). Every JSON body read from a registry is capped at 1 MiB (`capped`, `BODY_BYTES`), DID logs and status lists at 4 MiB (`issuers::get`), and ed25519 signatures are checked with `verify_strict`. **Nothing tells the wallet how an application goes**: the issuer has no messaging key since the vault went, so pairing names no DIDComm channel and the wallet opens no relationship with the issuer; the submit sheet (`submitCollect`) and Home's empty hint say to come back to catalog.almena.id to see how it stands and collect the credential (the catalog's own `receive` code). Issuer notices, the issuer's conversation and `registry_collect` were removed on 2026-11-12; they come back, if they do, with the key custody they need. To try it from the portal on macOS, `task build:debug` and open that bundle: `task dev` receives no links. Against a local registry: `REGISTRY_DID_URL=http://localhost:8000 task dev` in `../api`, then `cargo test registry -- --ignored`.
- Plugins per platform (`src-tauri/src/lib.rs`): `single-instance`, `window-state`, `autostart`, `notification` and the system tray on a computer (`notification`, `src-tauri/src/notify.rs`: a message that arrives by live delivery while the window is not focused becomes a system notification, saying as much as Profile → Notifications chose — everything, the sender, or nothing identifying (`src/notify.ts`, kept like the other device preferences and handed to Rust with the words in the interface's language); not on a phone, where the push plugin, a fork of this one, takes the same native symbols and push announces what arrives in the background) (`autostart`: a switch in Profile → Security, desktop only (`src/autostart.ts`); the login item — a LaunchAgent on macOS — starts the wallet with `--minimized`, and the window is minimised on `RunEvent::Ready`, since in `setup` it is not on screen yet; it starts locked, so nothing is received until it is unlocked) (`tray.rs`: closing the window hides it while the tray is up — live delivery keeps running — the left click and the macOS Dock bring it back, the menu's entries, named by the front end in its language (`src/tray.ts`), open the window and quit; `window.rs` hides and shows the window, emits `window-shown` so the auto-lock is checked on return, and puts a restored window on a screen that exists; the glyphs come from `assets/branding/tray` via `task icons`); `barcode-scanner` on a phone or tablet only, where the Scan QR tab appears (`platform_info` says so, `src/platform.ts`); `deep-link` everywhere, for `almena://` — the scheme the wallet's own invitations are written with — and on a phone for `https://almena.id/w/…` too (`tauri.conf.json`'s second mobile entry, `appLink`: the plugin writes the iOS Associated Domain `applinks:almena.id` and Android's `autoVerify` intent filter at every build; `push/ios/wallet_iOS.entitlements` carries the domain as well, since `push/sync.sh` copies it over the generated one). That is the form the API hands out (`deep_link`; `scheme_link` is the `almena://` one): only an app `almena.id` names in its `/.well-known/apple-app-site-association` and `assetlinks.json` can claim it. `src-tauri/src/links.rs` (`scheme_form`) reads it as the `almena://` link it stands for — that host, no port or credentials, under `/w/`, nothing else — and `registry::request_uri` reads requests through it; contact and mediator invitations are read from any URL with `_oob` already. A computer keeps `almena://`. A link or a scanned code is classified by `invitation_kind` and put to the person in a confirmation sheet over the open screen (`LinkSheet`, built on the generic `ConfirmSheet`: icon, origin, title, one line, detail rows, Cancel and Accept — meant for more cases later). `link_details` gives it only what the wallet knows: for a contact invitation the card's fingerprint (an invitation carries no name), the contact it already is, or that it is this wallet's own; for a mediator, it, the current one and how many contacts go through that (they move to the new one). Nothing is acted on until Accept, and a link that arrives while locked waits for the unlock (`src/links.ts`, `App.tsx`). The system learns the scheme from the bundle on macOS, iOS and Android, from the installer on Windows and from the `.deb`/`.rpm` on Linux; an AppImage registers itself at startup, and so does a Windows development build (`register_all`). `task dev` on macOS is not a bundle, so links do not reach it.
- Backup (`messaging/backup.rs`, Profile → Backup, `BackupSettings`): what the phrase does not bring back — the messaging state, every conversation, the credentials and the picture — in one file sealed like the files on the device (key `m/2'`, AAD `almena-wallet/backup/1`), saved and opened through the system's sheets (`tauri-plugin-dialog`, and `tauri-plugin-fs` for the paths and Android content URIs they return; only Rust calls them). Restoring merges under the messaging `Gate`: what the device holds wins — its mediator too: the file's mediations are taken only by a device with none, and the file's relationships on another mediator are `stranded` and moved at the next sync —, what the file adds is counted (`Restored`), and a second restore adds nothing. A file another identity sealed is `backup_not_this_identity`. The log of what was presented travels in it too (`presented`, absent from older files). **Reminder** (`src/backup.ts`, `backupDue`): when a credential arrived after the last backup made from the wallet and after the reminder was last put away, Home shows a card with Save a backup (the same export) and Not now; either quiets it until the next credential arrives. The two times are a device note in `localStorage` (`almena.backup.reminder`).
- `src/screens/onboarding/` — welcome, phrase, confirmation quiz, restore; then `PinSetup`. `App.tsx` decides between onboarding, the lock (`PinScreen`) and the tabs from `vault_status`. The phrase is written down, never copied: nothing puts it (or a PIN) on the clipboard; pasting into restore is fine. The phrase, the quiz, restore, the phrase check and `PinScreen` (so every PIN: setup, lock, change, biometrics) call `useShield` (`src/shield.ts`, counted so one screen handing over to the next keeps it up), which drives `screen_shield` (`src-tauri/src/shield.rs`): window content protection on Windows and macOS, `FLAG_SECURE` over JNI on Android, on iOS — where screenshots cannot be refused — a plain cover over the windows while the scene is not active, so the app switcher's picture holds nothing; on Linux nothing, there is no such API.
- `src/screens/HomeTab.tsx` — the first tab is where the credentials are: the greeting, then each credential held as a `CredentialCard` (`src/components/CredentialCard.tsx`: ID-1 proportions, the identity colour to its `--brand-strong` shade, guilloché arcs and the Almena mark — `BrandMark`, the mark drawn in `currentColor` — behind the words, the brand's ink; a `StatusChip` for how it stands), one under the other and two to a row on a wide window (`.screen--wide`). There is no category on a held credential, so every card wears `BadgeCheckIcon` and the word "Credential". What a card says comes from pure helpers in `src/credentials.ts`, tested in `credentials.test.ts`: `credentialName` (the type's name in the locale, its language, English, any, then its catalogue id), `issuerLabel` (name, else DID), `registryOf` (the host in `scope`), `standing` (revoked, suspended, invalid — a `signature` problem —, expired, valid, not checked, in that order) and `shown`. A card opens `CredentialScreen` on the tab's stack: the card, issuer, its DID, type, registry, dates, status with Check status, the claims, and Remove with its second confirmation. The list is held by `HomeTab`, so the detail and the list agree. Opening Home checks the statuses only when one was never read or not for ten minutes (`dueForCheck`), since Home opens at every unlock; its sync button checks them whenever asked. With nothing held, an empty wallet drawn in the identity colour (`src/components/illustrations/EmptyWallet.tsx`), the hint that credentials are asked for at catalog.almena.id, and a Scan QR button where that tab exists. Profile has no Credentials section: they are listed once, on Home.
- `src/screens/MessagesTab.tsx` — the inbox (`MessagesScreen`), a conversation (`ConversationScreen`) and its contact (`ContactScreen`, the alias), and what the "+" leads to: `NewConversationScreen` (the contacts). `InviteScreen` (QR from `src/qr.ts`, a dependency-free ISO 18004 encoder) and `AcceptInvitationScreen`: the invitation code is opened from the QR button at the top right of the Profile tab; an invitation is accepted from a scanned code or an `almena://` link. The third tab is Profile (`src/screens/ProfileScreen.tsx`): at the top the identity's picture and its name, shown only (`ProfileHeader`, over `Avatar`); the picture is shrunk to a 512-pixel JPEG in the interface (`src/photo.ts`) and sealed on the device by `messaging/photo.rs`, never sent. Under it a menu of sections in `src/screens/settings/`, each a screen of its own, the shape of the previous Almena ID wallet's settings: Profile (where the picture and the name are changed: `PhotoEditor`, `ProfileCard`), Appearance (identity colour, light/dark and the language: System — the default —, English, Español, each named in itself from its own catalogue; `src/i18n/locales.ts`, `resolveLocale` and `storedLanguage`, kept in `localStorage` as `almena.language` and held by `I18nProvider`, so it applies at once, tray and notification words included), Messaging (the mediator, `MediatorCard`: which one, how many messages wait, Change mediator, Disconnect after an inline confirmation that says how many contacts stop reaching you, and while a previous one is still collected, until when) and Security (change the PIN — `PinChange` —, biometrics — `PinConfirm` —, auto-lock after 1, 5 or 10 minutes of no use, where the record is kept, check the recovery phrase, sign out). Auto-lock (`src/autolock.ts`, `src/lock.ts`) drops the identity from memory rather than hiding it; the clock counts across time spent in the background and is checked when the wallet is seen again (`idleLeft`, the one sum the timer and the return both ask). A section is listed only once there is something in it. Messages arrive live while the wallet is visible (`src/live.ts` follows `visibilitychange`); screens also sync on opening and from their sync button. In the background the mediator notifies instead (`src/push.ts`).
- `src-tauri/gen/android`, `src-tauri/gen/apple` — native projects from `tauri android|ios init`; regenerated, so settings that must survive live in `src-tauri/Info.ios.plist`, `src-tauri/PrivacyInfo.xcprivacy` (the iOS privacy manifest), `src-tauri/push/` (applied by `push/sync.sh`, which also adds the privacy manifest, which the init tasks run; it patches the Xcode project instead of running xcodegen, whose output differs from Tauri's) and the Taskfile. `google-services.json` is the publisher's and is not committed.
- `assets/branding/` — source artwork; `task icons` regenerates `src-tauri/icons` and `public/brand`. Android launcher icons under `src-tauri/icons/android` are hand-drawn.
- Navigation: the four tabs are `App.tsx`'s `route`; inside a tab, screens are a stack (`src/nav.ts`, `useStack`: push, pop, replace; the first screen is never popped), so a way back returns to whatever led there — `HomeTab` (a credential's detail), `MessagesTab` and `ProfileScreen` (its sections and the mediator, PIN, device and invitation screens) use it. The device's preferences (identity colour, light/dark, auto-lock, notification privacy) are applied once at the root (the language by `I18nProvider`, above it, read through `useI18n`) and read through a context (`src/preferences.tsx`, `usePreferences`), not passed down.
- Back: every screen's back arrow is `BackButton`, which also offers it to Android's back button and gesture while it is on screen (`src/back.ts`, Tauri's `onBackButtonPress`, held only while there is somewhere to go back to); an open `ConfirmSheet` takes it as Cancel.
- The webview runs under a strict CSP (`tauri.conf.json`: `'self'`, `ipc:`, `data:`/`blob:` for pictures and fonts); `task dev` has none (`devCsp: null`), because Vite injects inline scripts.
- `src/styles/global.css` — the only place a colour is written; palettes keyed by `data-theme` and `data-accent` on the root. Each palette carries `--brand-strong` (the far corner of a credential's card) beside `--brand`, because `color-mix` is younger than the webviews; a status chip's states are `--state-*` on `--chip-bg`, the same in both themes.
- The identity colour is the person's choice, in Profile → Appearance (`src/appearance.ts`, `data-accent` on the root picks the palette in `global.css`): orange `#eb7229` (the default), blue `#2563eb`, red `#e0413a`, yellow `#f2b705`, green `#1f9d55`, cyan `#3fe0ff`, magenta `#d63384`, teal `#0fa3a3` — every portal's colour.
- Typefaces, as in the portals, bundled with the app (it works offline) from Fontsource packages imported in `src/main.tsx`: Chakra Petch (`--font-brand`: headings), Inter (`--font-sans`: the interface), JetBrains Mono (`--font-mono`: DIDs, the phrase, codes). Never load them from the network.

The look follows the previous Almena ID wallet (github.com/almena-id/wallet, branch `develop`).

## Rules

- Everything is written in English.
- The app is meant for the App Store and Google Play: a change that adds a permission, sends data off the device, or changes how the identity is removed must still meet their rules, and updates the list in `docs/store-publishing.md` (which links the guidelines, privacy declarations and agreements). Follow Apple's HIG and Material Design where the interface is platform-specific.
- User-facing text is translatable: English (`en`) is the source language, Spanish (`es`) the first translation. No hard-coded user-facing strings.
- Tasks live in `Taskfile.yml` (`task --list`). `build:macos` (development signing, for Touch ID) and `release:macos` (Developer ID, notarized, stapled) take their identity, profile and notary key from `.env.local` under names Tauri does not read (`MACOS_*`, `NOTARY_*`), so a plain `task build` never signs or notarizes; they write `src-tauri/.signing/` per build (ignored). The release tasks — `release:linux`, `release:windows`, `release:macos`, `release:android`, `release:ios`, each with `VERSION=2026.11.1` and run on the platform it builds — leave their artefacts in `release/` (ignored) as `almena-wallet-<version>-…`, with their keys from `.env.local` (`MACOS_*`, `NOTARY_*`, `ANDROID_UPLOAD_*`, `IOS_RELEASE_*`, optional `AZURE_SIGNING_*`); what they stamp (the version, the production push entitlement, what Tauri writes into the Xcode project) is put back afterwards. The version is stamped by `scripts/stamp-version.mjs`. GitHub Actions run those same tasks: `.github/workflows/check.yml` (pull requests and `develop`: `task check` plus the mobile `cargo check`s) and `.github/workflows/release.yml` (every push to `main`: year.month.sequence version from the `v*` tags, the five builds, a GitHub release with the computer installers and signed `SHA256SUMS`, then — after approval in the `stores` environment — Google Play internal testing and TestFlight), with the toolchain set up by `.github/actions/setup`. A workflow only turns secrets into the files and variables `.env.local` would name and calls `task release:*`; build logic goes in the Taskfile, never in a workflow. Every secret and variable is in `docs/releasing.md`. Before finishing a change: `task check` — `tsc`, ESLint (`eslint.config.js`: TypeScript's recommended rules and the two classic hook rules), Vitest (`src/**/*.test.ts`, no DOM: screens are tested through the pure helpers they draw from, and modules that reach Tauri with `vi.mock`), rustfmt, clippy and the Rust tests — and `task check:mobile` when Rust changed.
- Against a local mediator: in `../mediator`, `ALMENA_PUBLIC_URL=http://localhost:8080 task dev:memory`; (add `ALMENA_RATE_LIMIT=0` for repeated test runs), and for the move test a second one with `ALMENA_PORT=8081 ALMENA_PUBLIC_URL=http://localhost:8081`; then `cargo test -- --ignored` in `src-tauri`, or paste `http://localhost:8080` (or its `/oob?_oob=…` link) in Settings → Mediator. The iOS simulator reaches the host's `localhost`.
